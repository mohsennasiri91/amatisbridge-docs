۱. نمای کلی

این سند، چارچوب اتصال و تبادل داده از طریق آماتیس پل (AmatisBridge) را توضیح می‌دهد. آماتیس پل یک واسط یکپارچه‌سازی است که بین نرم‌افزار حسابداری یا منبع داده و سامانه مقصد قرار می‌گیرد. این مستند اصول پیکربندی درخواست‌ها، جهت حرکت داده، ساختارهای نمونه و نکاتی را شرح می‌دهد که هنگام اتصال یک API باید مشخص شوند. مسیرها، نام فیلدها و نمونه‌های این سند صرفاً نمونه‌اند؛ قرارداد واقعی هر اتصال باید بر اساس API سامانه مقصد و تنظیمات همان اتصال تعیین شود.

معماری

آماتیس پل واسطه‌ی تبادل داده است؛ ارتباط دو طرف به‌صورت زیر انجام می‌شود:

  • از حسابداری به سرور مقصد: آماتیس پل اطلاعات را از نرم‌افزار حسابداری یا منبع داده می‌گیرد، در صورت نیاز آن‌ها را به ساختار مورد انتظار تبدیل می‌کند و درخواست مناسب را به API سرور مقصد می‌فرستد.
  • از سرور مقصد به حسابداری: آماتیس پل اطلاعات را از API سرور مقصد دریافت می‌کند و آن‌ها را به منبع حسابداری یا سامانه متصل‌شده منتقل می‌کند؛ نحوه‌ی ثبت یا پردازش داده به اتصال و قابلیت‌های منبع حسابداری بستگی دارد.
نکته مهم: Push و Pull جهت تبادل داده را توصیف می‌کنند، نه اینکه خود آماتیس پل یکی از دو سرور باشد. آماتیس پل در میانه‌ی مسیر قرار دارد و درخواست‌ها و پاسخ‌ها از طریق آن مدیریت می‌شوند.

آدرس پایه (Base URL)

همه درخواست‌ها به یک آدرس پایه که آماتیس پل با آن فعال شده ارسال می‌شوند. مسیر هر Endpoint به این آدرس الحاق می‌شود.

مورد مقدار نمونه توضیح
base_url https://api.example.com/api آدرس پایه سرور مقصد؛ باید با https باشد (توصیه امنیتی)
endpoint /products نسخه API که در مسیر قرار می‌گیرد
آدرس نهایی {base_url}+{endpoint}
https://api.example.com/api/products		 ترکیب base_url + مسیر Endpoint
قاعده ساخت آدرس: endpoint+base_url
مثال: https://api.example.com/api + /products → https://api.example.com/api/products

قالب درخواست‌ها (Request Templates)

در آماتیس پل، برای هر عملیات یک قالب (template) تعریف می‌شود. این قالب مشخص می‌کند:

  • متد HTTP درخواست (GET، POST، PUT، PATCH، DELETE و ...) — کاملاً به‌صورت دلخواه در قالب تعریف می‌شود.
  • مسیر (path) نسبت به base_url (مثلاً /api/v1/products).
  • هدرها (احراز هویت، نوع محتوا و ...).
  • ساختار بدنه (body) یا پارامترهای Query.
  • نگاشت فیلدها از منبع داده به فیلدهای API.

نمونه‌ای از تعریف یک قالب در آماتیس پل:

{
  "template_name": "send_products",
  "base_url": "https://api.example.com/api",
  "method": "POST",
  "path": "/products",
  "headers": {
    "Authorization": "Bearer <API_KEY>",
    "Content-Type": "application/json"
  },
  "body_template": {
    "items": "{{products}}"
  }
}
مهم برای برنامه‌نویس سمت سرور: متد HTTP توسط قالب تعیین می‌شود و از پیش ثابت نیست. اگر در مستندات برای یک Endpoint متد POST پیشنهاد شده، سرور می‌تواند متد دیگری (مثلاً PUT) را هم پشتیبانی کند؛ کافی است قالب آماتیس پل مطابق آن تنظیم شود. توصیه می‌شود سرور برای هر Endpoint حداقل متدهای منطقی (مثلاً POST و PUT برای ارسال، GET برای دریافت) را پشتیبانی کند و در مستندات خود اعلام کند.

به همین ترتیب، برای عملیات دریافت (Pull)، متد پیش‌فرض GET است اما در صورت نیاز به دریافت شرطی یا ارسال پارامترهای پیچیده، قالب می‌تواند POST با بدنه نیز تعریف کند.

جریان داده

  1. کاربر در آماتیس پل، base_url، کلید احراز هویت و قالب‌ها را تنظیم می‌کند.
  2. نرم‌افزار داده را از سرور حسابداری یا منبع داده مشابه می‌خواند و به فرمت JSON تبدیل می‌کند.
  3. بر اساس قالب فعال، درخواست به Endpoint مقصد ارسال می‌شود.
  4. پاسخ سرور (موفق/ناموفق) در لاگ آماتیس پل ثبت می‌شود.

واژه‌نامه

اصطلاح توضیح
AmatisBridge نام لاتین همگام‌ساز آماتیس پل
base_url آدرس پایه سرور مقصد که کاربر تنظیم می‌کند
Push ارسال داده از نرم‌افزار به سرور
Pull دریافت داده از سرور به نرم‌افزار
Endpoint مسیر مشخص API روی سرور (نسبت به base_url)
Template / قالب تعریف قابل‌ویرایش درخواست شامل متد، مسیر، هدر و بدنه
Payload بدنه JSON ارسالی

۲. اصول مشترک

احراز هویت

همه درخواست‌ها باید شامل هدر احراز هویت باشند. این هدر در قالب آماتیس پل تعریف و به‌صورت خودکار به هر درخواست اضافه می‌شود: 

Authorization: Bearer <API_KEY>
Content-Type: application/json
Accept: application/json
نکته: در صورت نامعتبر بودن کلید، سرور باید کد 401 برگرداند.

فرمت پاسخ استاندارد

همه پاسخ‌ها باید ساختار یکسان داشته باشند:

{
  "success": true,
  "StatusCode": 200,
  "StatusDescription": "عملیات با موفقیت انجام شد"
  "data": { ... },
  "ErrorMessage": null
}

کدهای وضعیت HTTP

کد معنا کاربرد
200 OK دریافت موفق (GET) یا پردازش موفق
401 Unauthorized کلید نامعتبر
403 Forbidden مجوز لازم وجود ندارد
404 Not Found منبع یافت نشد
500 Server Error خطای داخلی سرور

نسخه‌بندی

اگر API مقصد نسخه‌بندی دارد، نسخه را مطابق مستندات همان سامانه در URL قرار دهید؛ برای نمونه /api/v1/.... این الگو برای همه‌ی APIها اجباری نیست و آماتیس پل نباید بدون نیاز، مسیر نسخه را به URL اضافه کند.

۳. Endpoint های ارسال (Push)

متد HTTP هر Endpoint در این بخش، پیشنهاد است. متد واقعی در قالب آماتیس پل تعیین می‌شود و می‌تواند متفاوت باشد. سرور مقصد باید در مستندات خود متدهای پشتیبانی‌شده را مشخص کند.

۳.۱. ارسال محصولات

POST {base_url}/api/v1/products

آماتیس پل لیست محصولات را از سرور حسابداری یا منبع داده مشابه خوانده و به این Endpoint ارسال می‌کند. متد واقعی توسط قالب نرم‌افزار تعیین می‌شود (پیشنهاد: POST یا PUT).

درخواست (Request)

POST {base_url}/api/v1/products
Authorization: Bearer <API_KEY>
Content-Type: application/json

{
  "mode": "immediate",
  "create_if_not_exists": "true",
  "products": [
    {
      "sku": "123",
      "name": "محصول تست",
      "price": 5000,
      "stock": 4,
      "discount": 1000
    },
    {
      "sku": "456",
      "name": "محصول تست 2",
      "price": "5200",
      "stock": "55",
      "discount": null,
      "post_meta": [
        {
          "meta_key": "unit",
          "meta_value": "عدد"
        }
      ]
    }
  ]
}

فیلدها

فیلد نوع الزامی توضیح
sku string ✅ کد یکتای محصول
name string ✅ نام محصول
price number ✅ قیمت
stock integer ✅ موجودی
discount number - nullable ❌ زمان آخرین به‌روزرسانی
post_meta array ❌ دیتای اضافی به صورت آرایه ای از کلید - مقدار

پاسخ موفق

{
  "success": true,
  "data": {
    "mode": "immediate",
    "total": 3,
    "created": 1,
    "updated": 2,
    "failed": 0,
    "results": []
  }
}

۴. Endpoint های دریافت (Pull)

متد پیشنهادی برای دریافت، GET است؛ اما در صورت نیاز به دریافت شرطی با بدنه (مثلاً لیست شروط پیچیده)، قالب آماتیس پل می‌تواند POST تعریف کند. سرور مقصد باید متدهای پشتیبانی‌شده هر Endpoint را اعلام کند.

۴.۱. دریافت سفارش ها

GET {base_url}/api/v1/orders?limit=20&status=pending&from=2026-10-20&to=2026-10-25&ignore_errored=true

آماتیس پل با این Endpoint لیست محصولات را می‌گیرد تا در سرور حسابداری یا مقصد درج کند.

پارامترهای Query

پارامتر نوع توضیح
limit int تعداد در صفحه
status stirng وضعیت سفارش ها - چند وضعیت با "," از هم جدا میشوند.
from string تاریخ قدیمی ترین سفارش
to string تاریخ جدیدترین سفارش
ignore_errored string نادیده گرفتن سفارشهایی که قبلا خطا داشته اند
